## 1. WhisperLiveKit (QuentinFuxa) — the most reusable server design
- URL: https://github.com/QuentinFuxa/WhisperLiveKit · License: **Apache-2.0** (some bundled models differ: FunASR SenseVoiceSmall own license, Canary CC-BY-4.0)
- Activity: last push **2026-10-01**, repo updated 2026-10-12, ~11.1k stars, Python
- What it is: FastAPI self-hosted ASR pipeline with streaming translation + diarization. WebSocket `ws://localhost:8000/asr`, OpenAI-compatible REST, Deepgram-compatible WS. Per-session `language`, `target_language`, `context`, `mode`.

**Design lessons (high value):**
- **"Stable-prefix / append-only" commit rule.** Never re-send or rewrite already-shown text. Three named policies: **LocalAgreement** (confirm a prefix once N consecutive updates agree), **AlignAtt** (attention-gated commits), and Qwen3 causal "stable-prefix rule." This is the canonical fix for your "incremental translation flicker/rewriting" concern.
- **Bounded-recompute / causal encoders** for long sessions: `qwen3-streaming` causal mode encodes each ~2 s block exactly once, bounded 15 s window + sentence-boundary resets → **constant per-chunk compute, append-only transcripts, unbounded session length**. Directly addresses "long-session latency accumulation."
- **Segment on VAD pause**: `--pause-segmentation-seconds` (default 5.0) creates a stable transcript boundary when a pause exceeds the threshold; `--asr-coalesce-min-s` defers ASR until enough new audio accrues (trades cadence for fewer encoder passes).
- **Translation commit policy is separate from ASR commit**: `--translation-backend nllb` (in-process) vs `alignatt` (sidecar, "attention-gated append-only commits"); `--translate-on-complete` holds source tokens until a segment finalizes (fewer partial updates). `docs/translation-alignatt.md` has `quality/balanced/low` latency policies and warns "policy settings, not measured latency guarantees."
- **A dedicated caption-display layer** (PR #449, created **2026-09-10**) is worth copying conceptually: it splits "sentence derivation + display rules" from the MT layer; typed events (transcription/translation × provisional/final); **"a finished sentence is held and always shown; a sentence flips to final style in place; final text never visibly shrinks or rewords."** `--event-log` records JSONL for replay/testing.
- **Explicit warnings** in README: Whisper auto-detect "tends to bias towards English"; Qwen3 needs explicit `--language` because "automatic detection switches language mid-stream on accented audio"; diarization "does not add simultaneous-speaker output" (one speaker per token).
- **Issues that document real bugs:**
  - **#365** (2026-05-28) *Cumulative timestamp drift due to VAD delay double-counting*: Silero VAD end-events can point into the previous PCM chunk → silence double-counted → `cumulative_pcm_duration_stream_time` inflates → **timestamps drift progressively later in long streams**. This is a concrete "long-session latency accumulation" root cause and fix (clamp VAD timestamps to chunk bounds).
  - **#150** "Echoed transcriptions" (repeated output, tiny model) — same class of problem RTranslator users hit.
  - **#264** (2025-10-20): user asks to translate only when the sentence segment completes, "because changing the translation multiple times makes it a bit difficult to follow" — i.e., flicker is real and users want commit-on-complete.
  - **#455/#456** (security/ops): no cap on concurrent WS sessions, one ffmpeg per connection never idles out; AlignAtt sidecar sends transcript over unauthenticated WS. Practical long-session resource warnings.

## 2. RealtimeSTT / RealtimeTTS (KoljaB) + ecosystem
- RealtimeSTT: https://github.com/KoljaB/RealtimeSTT — **MIT**, last push **2026-09-17**, ~10.2k stars
- RealtimeTTS: https://github.com/KoljaB/RealtimeTTS — **MIT**, last push **2026-10-09**, ~4.0k stars
- **stream2sentence** (same author): https://github.com/KoljaB/stream2sentence — **MIT**, last push 2026-08-25
- **echoff** (same author): https://github.com/KoljaB/echoff — **MIT**, last push 2026-08-27 — "Stops your voice agent from transcribing its own voice"
- RealtimeVoiceChat: https://github.com/KoljaB/RealtimeVoiceChat — **MIT**, ~3.9k stars, **no longer actively maintained** (last push 2025-07-11)

**Design lessons:**
- **Two-lane transcript design (RealtimeSTT)**: a fast, replaceable "realtime" lane + a single authoritative "final" lane. On CPU it pairs **Nemotron streaming** (processes only new frames) with **Parakeet** refining the complete turn once at finalization — explicitly to avoid "repeatedly retranscribing a growing audio buffer while preserving a high-quality final." Docs also expose an "ultrafast" lane whose accepted words are **"sticky" within a generation** and note "Final transcription is unchanged and never consumes the merged preview text."
- **Latency/queue knobs (docs/configuration.md)** that map directly to your concerns: `realtime_processing_pause` (0.2 s idle between realtime attempts; lower = more load), `allowed_latency_limit` (default **100** unprocessed chunks before old chunks may be dropped — an explicit backlog-drop policy), `post_speech_silence_duration` (0.6), `early_transcription_on_silence`, `deactivity_silence_confirmation_duration` (0.16).
- VAD: layered Silero + WebRTC, `silero_sensitivity` 0.4, `webrtc_sensitivity` 3, `warmup_vad`.
- **echoff = the echo/feedback design pattern you asked for.** It aligns **system-audio loopback (render reference) with mic capture** on separate streams, maps both into one monotonic clock, fixes one startup offset, then feeds each reference frame just before its matching mic frame into **WebRTC AEC**. Key warnings: don't use the streaming adapter for "two independently clocked physical devices"; blocking the pairing callback stalls echo removal; `echo_path_ready` "is a readiness heuristic, not proof that all echo has been removed" (needs 10 dB reduction sustained 250 ms); "The application decides whether it should gate VAD or barge-in." Note it does **not** solve the headset case by itself — it's the software-AEC layer for speaker playback.
- **stream2sentence = the TTS-queue/backlog pattern.** Feeds an LLM/MT token stream through context-window + rule-based (NLTK) consensus checking to yield the earliest *safe* sentence boundary; `quick_yield_*`, `minimum_first_fragment_length`, `force_first_fragment_after_words`, `fragment_lookahead_words` exist specifically to cap first-chunk latency. This is how you avoid a TTS queue that only starts after a full sentence.
- **RealtimeTTS queueing**: `TextToAudioStream.feed()` accepts an iterator so "text can arrive while audio is already playing"; supports pause/resume/stop and fast cancellation (QwenEngine "native 24 kHz PCM streaming, fast cancellation"). Orientation latency: ~35 ms engine TTFT + ~35 ms to first PCM, RTF 0.108 on RTX 4090.
- Related issues: RealtimeSTT #156 "How to handle interruptions better while building speech to speech pipeline?"; #288 (2025-11-10) "Realtime translation possible?" (no built-in translation — `translator.py` is a test using OpenAI); RealtimeTTS #232 "StreamPlayer use TextToAudioStream queue instead of engine's one"; #33 async-queue vs threads; #360 "Memory usage grow over time?".

## 6. RTranslator: why it is turn-based (what the issues actually say)
- Issue **#176** "[Feature request] Single-Device Real-Time Translation (No Bluetooth Required)" (opened **2026-04-01**). Maintainer **niedev** reply (2026-04-01) is the key design rationale:
  - "Processing and translating audio word-for-word isn't currently possible. Besides being quite complicated to implement, it would result in a **significant loss of quality**, which I believe is the most important thing."
  - **Why two phones beat one (their echo/overlap argument):** "with two phones and two Bluetooth headsets, you have two microphones that capture the voice independently, and two separate audio streams. **The speaker doesn't hear their own translation, but only the other's.** Furthermore, **both people can speak simultaneously without any issues**; it's much more natural." → i.e., the app is turn-based precisely to avoid self-echo and overlapping speech; two physically separated mics+streams are their echo-cancellation strategy.
  - Forward-looking: they will speed up Walkie-Talkie and "if you connect Bluetooth headsets, I will not deactivate the mic during the speech (if possible)" to approach true simultaneity.
- Issue **#106** comment (niedev, **2025-02-15**): "The Walkie-Talkie mode isn't the real time mode of RTranslator"; for real time use Conversation mode with BT headphones — and you can "reduce the time of silence required to send the message... to have a faster translation, **sacrificing some quality**." Also states the echo problem plainly: "From what I know it's **impossible to not pick the audio of a video**, the mic of your phone will pick every audio it hears, even if it comes from your speakers." And the background-throttling problem: "some phones will limit the use of the CPU for background apps... performance will be reduced so much that it will practically stop working until you reopen it."
- Issue **#81** (2024-10-06) "[BUG] When translating, the translation result will keep adding text" — user-visible **incremental accumulation/rewriting** bug (Chinese→English). Issue **#155** (2025-09-09) Walkie-Talkie voice input broken on **Android 15**. Issue **#147** (2025-07-30) user proposing a Bluetooth earpiece product asks the maintainer to collaborate.
- README states: Conversation mode requires two connected phones; "Sometimes the Bluetooth connection drops"; ≥6 GB RAM recommended; NLLB is non-commercial-licensed.

**Other explicit "simultaneous is hard" statements:**
- Hibiki: needs synthetic aligned same-speaker data because it "does not exist in significant amounts"; only FR→EN; 40 s context.
- RTranslator: word-for-word simultaneous means "significant loss of quality" (above).
- WLK docs: AlignAtt results "don't transfer automatically" across ASR backend/hardware/buffering; AlignAtt latency modes are "policy settings, not measured latency guarantees."
- Twilio sample: translation prompt "waits for a full turn before translating"; they offer audio-forward playback "to minimize perceived silences."

## 7. Cross-cutting design patterns (the transferable lessons)

**Echo / feedback loop (the single biggest mobile issue):**
- Sokuji's `docs/github-issues/issue-55-comment.md` is the clearest write-up: browser **AEC cannot use AudioWorklet-generated audio as its reference signal**, so a `wav_stream_player` that connects an `AudioWorkletNode` straight to `context.destination` is invisible to AEC → the old **passthrough** function created a positive feedback loop (mic records speaker → passthrough sends it back → plays again → amplifies).
- **Fixes they adopted** (all directly reusable): use `getUserMedia` constraints `echoCancellation:true`, **`echoCancellationType:'system'`**, and `suppressLocalAudioPlayback:true`; play translated audio through a standard `<audio>`/`HTMLAudioElement` (which *is* visible to AEC), **not** an AudioWorklet; keep a muted `dummyGain` node so processing continues without feedback; and **"the most reliable solution for speaker mode is headphones"** — physically breaking the loop.
- Android equivalent: rely on **hardware AEC/NS/AGC** where available (Deepgram agent), require a **physical device** to test it, and where you must play while recording, prefer a headset (or system-audio capture instead of mic, as ALAD does).
- Roland: **echoff** shows the general software approach if you truly must play over speakers: capture a loopback *render reference*, align it to the mic on a shared monotonic clock, and run WebRTC AEC — and still gate VAD/barge-in yourself.

**Committing translations without flicker (your "incremental rewriting" concern):**
- Adopt an **append-only / stable-prefix** contract; never reword already-shown text. WLK's caption layer: finished sentence "held and always shown," flips final "in place," and "final text never visibly shrinks or rewords."
- Offer a **translate-on-complete** mode for users who prefer fewer partial updates (WLK #264 request; RTranslator and voice-bridge both choose whole-sentence output for quality).
- Keep **provisional (draft) vs final** as two explicit lanes with tests; make the draft path optional per backend (WLK caption events).

**TTS queue / backlog (your "TTS queue backlog" concern):**
- **Prefetch the next sentence's TTS while the current one plays** (WarpTalk PR #211, `TTS_PREFETCH_WHILE_PLAYING`, opened 2026-10-01): baseline showed the tail was *not* model time but the "chunk publish → TTS start" gap (p50 3.3 s, p90 7.4–10.6 s), caused by holding a per-(speaker,language) lock until the sentence was *heard*. Prefetch took the inter-sentence gap "from about TTFA (0.6 s p50, up to 3.7 s p90) to about 0." Crucial caveat they document: **dubs usually run longer than the speech they translate, so a backlog builds up naturally through a long turn**, and a **fixed-speed drain cannot recover from bursts** (voic #36: queue of ~2 min, drains at 1.25× realtime, "nothing catches up" — their options are cap+drop, or pace against the sink's playhead acks, and they must coordinate with barge-in `clearAudio`).
- So: cap the queue near realtime and **drop** excess; pace against playback acks, not a fixed sleep; keep strict FIFO per track; and never interleave sentences (tests should pin "no overlap by construction").

**VAD tuning:**
- Segment on **pause threshold** (`--pause-segmentation-seconds` 5.0) and on **silence endpointing** (danngalann: 800 ms → final; RealtimeSTT: `post_speech_silence_duration` 0.6).
- **Clamp VAD event timestamps to the current audio chunk** or long sessions drift (WLK #365).
- Keep VAD **separate from ASR** and do not enable two VADs at once (WLK keeps FunASR's internal VAD off; Sokuji/others let the app decide gating).

**Long-session latency accumulation:**
- Use **causal / bounded-window encoders** (each block encoded once) rather than re-encoding a growing buffer; reset at sentence boundaries.
- Avoid a **single unbounded buffer**; rolling windows + commit-and-trim (whisper_streaming buffer trimming on confirmed sentence/segment).
- Cap session/connection resources: WLK issues flag "no cap on concurrent WS sessions" and per-connection ffmpeg leaks; Gemini Live forces a **~10-min WS close** — plan **session resumption + context compression** and expect a brief reconnect pause.

**Bluetooth routing (what the sources say, and the platform rule):**
- RTranslator's approach: **two phones + two BT headsets** so each party hears only the other's translation — sidesteps self-echo entirely; they note "sometimes the Bluetooth connection drops."
- AlfredAI advertises BT routing but documents nothing; ALAD lists BT-headset mic only as roadmap. **No source demonstrates a clean single-phone mic→BT-headset simultaneous loop**, which reinforces the maintainer's "hard to implement without quality loss" point.
- Platform fact (Android docs, verified in `AudioManager` reference, fetched 2026-10-12): `startBluetoothSco()` / `stopBluetoothSco()` are **deprecated in API level 34**; the replacement is **`AudioManager.setCommunicationDevice(AudioDeviceInfo)`** / `clearCommunicationDevice()`. Budget for SCO-mode latency and route via `setCommunicationDevice`, and test AEC on a physical device.

## Most transferable design lessons (short list)
1. **Commit text append-only with a stable-prefix/LocalAgreement rule; treat provisional and final as two lanes and never reword shown text.** (WLK, RealtimeSTT)
2. **Split ASR into a fast replaceable lane + one authoritative final lane** to avoid re-transcribing a growing buffer. (RealtimeSTT Nemotron+Parakeet)
3. **For simultaneous translation, prefer "commit when predictable from source" (hibiki) or translate-on-segment-complete** — don't translate word-by-word; users and maintainers both report quality loss and flicker.
4. **Prefetch TTS of sentence N+1 while N plays; cap the playout queue near realtime and drop/pacing-correct the excess** — dubs are longer than source speech, so backlog accrues naturally. (WarpTalk #211, voic #36)
5. **AEC needs a reference signal it can see: play via standard audio elements / `suppressLocalAudioPlayback` + `echoCancellationType:'system'`, not an AudioWorklet; for speaker mode, recommend a headset.** Software path = loopback-reference alignment + WebRTC AEC (echoff). (Sokuji issue-55, echoff)
6. **Single mic owner on Android**; consumers (classifiers, etc.) copy the stream — never open a second mic. Use `VOICE_RECOGNITION` + hardware AEC/NS/AGC and test on a physical device. (danngalann client, Deepgram agent)
7. **Tune VAD as explicit knobs (pause segmentation, silence endpointing, min-speech) and clamp VAD timestamps to chunk bounds** to stop cumulative drift in long sessions. (WLK #365, RealtimeSTT config)
8. **Use bounded/causal windows with sentence-boundary resets** for unbounded sessions; plan for forced connection resets (Gemini ~10 min) and background-CPU throttling on Android. (WLK causal mode, live-translate, RTranslator #106)
9. **Split system-audio capture from mic capture** where possible (dubbing/captions vs. room conversation) to dodge room noise and echo. (ALAD vs. live-translate)
10. **Two-device (two-mic) topology is a legitimate architectural answer to the echo/overlap problem** — RTranslator is turn-based on one phone on purpose; true simultaneous needs either separated audio paths or model-level simultaneity (hibiki).
